Files & diagnostics

Handing a page to a studio (.psd)

File ▸ Export layered PSD writes the page as Photoshop layers — one way. Folders arrive as groups (pass-through folders stay pass-through), all blend modes map, clipping and Japanese layer names survive. QUIRKS: layer masks are baked into the pixels (what you saw is what they get, but the mask is no longer editable there); tone, fill, frame, balloon and text layers export as their rendered pixels; vector layers export as ink. This is an EXPORT — the app never reads .psd back, and your working file stays .ora/.mnc.

Export finish (print presets)

Export never upsamples. The Finish picker in Export All Pages bundles output dpi, colour mode (mono 1-bit / grayscale / full colour), resample kernel and file format. Asking 600 dpi of a 350 dpi work exports at 350 — the dialog says so before you pick a folder, because inventing detail to hit a printer's number is a lie in a file.
Mono thresholds AFTER the resample. A 1-bit finish taken before the downscale would be averaged straight back into grey by the filter; the order here is what makes the file genuinely two-tone. Editing any control flips the picker to Custom — a preset is a starting point, not a lock.

Where the log lives

manganakama.log, beside the exe — or in %LOCALAPPDATA%\MangaNakama\. One block is appended per session. If the install folder is read-only the log silently moves to the local-app-data fallback; F1 shows the resolved path (with a copy button) so you never have to guess which one is live.

Where your settings live

prefs.txt, beside the exe — and deleting it is a supported way to undo a setting you cannot find. Everything in Edit ▸ Preferences… is stored there as plain name=value lines you can read and edit in Notepad. A missing file is not an error: the app starts on the shipped defaults and says nothing. Neither is a damaged one — a line that makes no sense costs you that one setting, not the file, so the other nine still load. It is deliberately not ui.txt, which holds the palette layout and is the file to delete when a palette has ended up somewhere unusable; wiping your window layout was never meant to also wipe your settings, so the two are apart.

Reading a crash

A clean session ends with === exited cleanly ===. A block that ends any other way — mid-line, or at a !!! PANIC at file:line entry — is the crash record. The panic hook chains into the log with the exact file and line; the missing tail matters as much as the line, because a stack-overflow class kill leaves no Rust hook output at all. The banner and the F1 page both carry the build's version and short SHA — say them with the report.

After a crash: the recovery offer

If the last session did not exit cleanly, the next start asks whether to open the autosave. The question is answered from the log, not from a marker file — the same missing exited cleanly line described above is what triggers it. You are only ever offered an autosave that is newer than the file it belongs to, so a saved document is never shadowed by older work; saying No changes nothing on disk and the autosave stays where it is. Autosaves land beside the document as <name>.autosave.mnc, or in %TEMP% as MangaNakama-autosave.mnc for a document you have never saved. Saving normally deletes the matching autosave, because the saved file is the better copy by then. Work folders never appear in this prompt — they autosave in place, page by page, so after a crash the folder is already current.

Turning the autosave down — or off

Edit ▸ Preferences ▸ Autosave sets the interval, and Off means nothing is written at all. Not "written rarely" — the timer is never started, so there is no recovery copy to offer after a crash and a work folder stops saving itself in place. That is a real choice on a slow drive with a huge page, but it is the one setting here that can cost you an afternoon, so it is worth knowing what it turns off. The interval takes effect immediately; you do not have to restart.

Is my pressure real?

If the tablet stops reporting pressure, MangaNakama keeps drawing at a constant half-pressure — and tells you. A pen that reports no pressure must still be able to draw, so the value is substituted rather than refused; what would be unfair is substituting it in silence, because then "my pressure stopped working" is impossible to confirm from inside the app. So: the first pen touch of a session writes one line to the status bar and the log (pen · pressure: reported …, or NOT REPORTED — 0.5 substituted in the warning colour), a loss part-way through a session announces itself the same way, and F1 marks the value permanently — pressure 0.500 (SUBSTITUTED — device reports no pressure). If your tablet driver's own test page shows pressure and this says NOT REPORTED, the loss is between the driver and Windows Ink, not inside the drawing app — which is the one thing this distinction is for.

The pen moves and nothing is drawn

A stroke that received no usable input says stroke drew nothing in the status bar instead of just producing no ink. MangaNakama only paints from pen reports that Windows marks as actually touching the tablet — that filter is what keeps a blob from appearing at the start of every stroke — but a few drivers signal contact by pressure alone and never set the flag. The message names where the pen went down and whether reports arrived and were filtered out (… 7 pen report(s) dropped as not-in-contact) or never arrived at all, which is the difference between a driver problem and a tablet that is not talking to Windows. The F1 page carries the running totals on its pen device row.

How far behind the pen is

F1 shows end-to-end input latency — from the moment the tablet stamped a sample to the frame that showed it — with a session maximum beside it. It reads — (pen only) for mouse drawing, because the mouse fallback has no device clock to compare against and a made-up number would be worse than a blank.
Also after every operation writes the recovery copy the moment an operation finishes, instead of waiting for the timer. It does not replace the interval — with both on you get whichever comes first — and it is the same write to the same file, only on a different trigger. Undo counts as an operation; a stroke does not count until you lift the pen, and adding or deleting a layer counts too. It is off by default, because on a print-resolution page that write is not free: turn it on for the session you cannot afford to repeat, not as a permanent setting. The checkbox greys out when Autosave is Off, because Off means off.

Which path inks your strokes

The first launch measures this machine in the background, and the answer applies from the NEXT launch. Nothing becomes the default on your hardware without a measured number, so the first start stays on the CPU path and spawns a one-shot benchmark as a separate windowless process — it times five brush classes on both paths, writes down what it found and exits. Inking moves to the GPU only if that run said it was clearly faster: the strategic class (the big soft airbrush, where cost scales with the tip's area) has to win outright, and nothing may lose badly, so a knife that pays 1.5× vetoes even a 2× airbrush win. If the measuring process dies, no verdict is written and the next launch simply tries again.
gpu-verdict.txt beside the exe holds the verdict — delete it to re-measure. Three lines: which adapter was measured, on or off, and the ratios as a note for humans. The adapter line is the identity, so a driver update or a new GPU re-measures by itself; a damaged file counts as no file rather than deciding anything.
The View menu always wins, and sticks. View ▸ GPU inking is an explicit choice: it is remembered in ui.txt, it is never overruled by a measurement, and once you have set it the app stops measuring. It takes effect from the next stroke, so flipping it mid-page is safe. On an adapter that cannot run the path at all the item is greyed rather than dead, and a ui.txt carried to a weaker machine just stays on the CPU.
Only the speed differs. Undo, masks, wash, smudge, erasing, textured tips — everything behaves the same either way, and the two paths are held to the same pixels by tests. If a drawing behaves differently with the switch flipped, that is a bug worth reporting, not a setting.
A brush that washes AND smudges at once always inks on the CPU, even with GPU inking on. That combination picks its colour from the canvas under the stroke while the stroke is still wet — every dab has to see the paint the dab before it just laid down, so the engine must work dab, look, dab, look. The GPU is only fast because it draws many dabs in one batch, and dabs in a batch cannot see each other's paint; for a brush whose whole character is that self-feedback, the colours drift visibly off — about 19% in our measurements, not a rounding error. Wash alone and smudge alone do not feed on themselves this way, and they do run on the GPU. Making the GPU stop and wait after every single dab would leave it slower than the CPU it was meant to replace, so the honest routing is: this one brush family stays where it is correct AND fastest. It is automatic — there is nothing to set, and no wet stroke ever comes out the wrong colour to buy a speed number.

Reporting a problem

Attach manganakama.log — one file, safe to post. The log is written to contain nothing personal: no file paths, no user names (a test fails the day any line leaks one). Its neighbour recent.txt is different — that one stores full opened-file paths including your Windows user name, so it stays private; the log is the file strangers can read.

Several documents at once

Every open document is a tab above the canvas, and File ▸ New opens a NEW one instead of replacing what you have. Click a tab to switch; the dot on a tab means unsaved changes. Each tab keeps its own pages, its own file, its own undo history — and its own view position, so switching back finds the canvas exactly where you left it. The × on a tab closes that document, not the application — except on the last one, where it closes MangaNakama (and still asks about unsaved work first), because there is nothing to show with no document open.

Dropping files on the window

An image dropped anywhere on the window becomes a layer in the document you already have open — the drop point does not change what happens. This is deliberately not what Clip Studio does: there, dropping on the canvas builds a new document and only the Layer palette imports. Here the common drop is a reference photo onto the page in progress, so that is what a drop means everywhere, and "open it as its own document" has its own gesture: drop a .mnc or .ora — or the work folder itself — and it opens. Drop several images and they all come in, in the order the shell hands them over. If a drop contains a project and images together, the project wins and opens. Readable formats are png, jpg, bmp, tif, webp and gif; anything else is refused in the status bar with its name rather than silently doing nothing.
Import an image while a selection is active and it arrives already masked to that selection. Select the panel, drop the photo, and everything outside the panel is hidden — no cropping, no erasing. It is a layer mask, so nothing was thrown away: Layer ▸ Layer Mask ▸ Delete mask and the whole photo is back, at full size, exactly where it landed. This holds for both routes in — the drop and File ▸ Import Image as Layer… — and the status bar says which of the two imports you got. With no selection there is no mask (an all-hidden layer would just look like a failed import).
An imported image lands ready to be placed. Anything bigger than the page is scaled down to fit first (never scaled up — enlarging a small asset is a guess, and this is where you make it by hand), and the transform box opens straight away: drag inside to move, the corners to scale, outside to rotate, Enter to commit, Esc to cancel. With a selection active the transform stays shut — the selection already said where the image goes. File ▸ Import Image as Draft… is the same import with the draft flag set, for a reference photo or a scanned rough: it shows on screen and never reaches the export.
Import a photo as a PAGE and it becomes a page of your paper, not the photo's. Photograph your ネーム, then Pages ▸ Import Page: the new page is built from the work's own page setup — trim, bleed, 基本枠, dpi — and the photo goes in scaled to fit, at the bottom of the stack, as a draft layer you draw over and never print. If the photo is a different shape from the paper it is fitted with margins and the status bar says so; the paper is never reshaped to match one photo. Same for Replace page with file. A plain single-image document has no paper to inherit, so there an imported image still makes a page of its own size.

Saving

Single images save as .ora; comics are work folders (a work.mnc index plus one file per page). Work folders autosave in place, page by page — only pages that changed are rewritten. Layered PSD is the hand-off format for other apps; CSP cannot open .ora.
Saving one page of a comic as .ora keeps its resolution but not its page setup. The file records the dpi it was drawn at, so tones come back screened exactly as you left them; the paper, trim, bleed and inner border do not travel, so guides stay off until you open the work itself again.

Exporting every page

File ▸ Export All Pages… asks for its options first, then for a folder. Leave the options alone and you get what you always got: <work name>-p001.png, -p002.png and so on, full resolution, PNG. An unnamed work exports as page-p001.png. Clearing the file prefix does not produce files called -p001.png — an empty prefix falls back to the work name.
A page range does not renumber. Exporting pages 5 to 8 writes p005 to p008. The number in the filename is always the page's own number, so a partial re-export overwrites exactly the files it should.
Split spreads writes a spread as two files, …p003a.png and …p003b.png — and a is the half a reader meets FIRST. On a right-bound (Japanese) work that is the RIGHT half. The seam is cut with no gutter, so nothing is thrown away; the gutter swallow only happens when you split a spread while editing. A page counts as a spread if you combined it this session, or if its canvas is half again as wide as a normal page in the work — the second test is what still works after the work has been closed and reopened, because the first is only remembered until you quit. In a work where every page is the same width nothing is treated as a spread.
Resample: Comic keeps hairlines, Photo smooths — and only a 1-bit finish can tell the difference. This is CSP's 処理方法 (イラスト向き / コミック向き). A smooth photographic filter averages a 1 px black line into grey on the way down, and the 1-bit threshold that runs afterwards then throws that grey away — the line is simply gone from the file. Comic averages the page's ink coverage instead and re-thresholds low, so a thin dark line survives the shrink. It is the default, and it does nothing at all to a grey or full-colour finish (there is no threshold there to bias), which is why the control greys out unless the Colour box says Monochrome. Pick Photo if you want the old behaviour back.
Format: PNG is the file a printer gets, JPEG is the copy you send an editor. 入稿 and 提出 are different jobs. The Proof JPEG 150 dpi finish is the second one ready-made: small files a phone opens, spreads kept whole so the reading order survives, page numbers still in the filenames. The quality box (85 out of the box) only applies to JPEG; it keeps its value while PNG is picked. A monochrome finish written as JPEG comes out as a grey JPEG of the thresholded page — JPEG cannot hold 1 bit, and the useful answer for a proof is the page you actually drew, not a refusal. Never send that file to a printer.

Sending the text to a translator

File ▸ Export Text (script)… writes every balloon in the whole chapter to a .txt, in reading order. The same toggle lives in the Export All Pages options, where it drops <prefix>-text.txt into the image folder. Layout: a == Page N == line for every page (even an empty one, so the numbers stay countable), then -- Panel N -- using the same panel numbering the Layers palette badges show. Text that sits in no panel comes last under -- Outside panels --; on a page with no panels at all it simply follows the page line.
One balloon is one line, and hidden text is not exported. Line breaks inside a balloon are typesetting, not content, so they collapse to a single space — expect a space where a Japanese balloon wrapped. A balloon that straddles two panels is filed by its centre point. A text layer with its eye off, or inside a folder with its eye off, is left out entirely: the dump is what would print.
The .txt is UTF-8 with a byte-order mark and Windows line ends. That is deliberate — the file leaves the app for Notepad, Word and Excel, and without those two details Japanese arrives as garbled characters or as one endless line. MangaNakama's own settings files are not written this way.
